# AjoLedger — Challenges Log

Real problems hit while building this, and how I solved them — the messy part in between the ADRs (decisions made before writing code) and HOW_IT_WORKS.md (how the finished mechanism works).

## Deciding not to track payout amounts/accounts in CirclePayout

**Date:** 2026-08-13
**What I was trying to do:** Model a way to track a circle's rotation payouts — who was paid, in which round — and considered also recording which account received the money (personal balance vs. a lien/collateral account) once that idea came up.
**What went wrong:** I almost added an `account` reference (and implicitly, an amount) directly to the `CirclePayout` entity so the record would show exactly where payout money landed.
**Why it happened:** I hadn't yet checked that idea against ADR 0004's reasoning — that actual money movement (crediting accounts, in whatever split) is deliberately the ledger's job alone, so there's one source of truth for where money went. Adding amount/account fields to `CirclePayout` would have created a second, parallel record of money movement that could drift from whatever the real ledger transaction eventually records.
**How I fixed it:** Kept `CirclePayout` as a pure rotation-schedule fact — circle, recipient, round number, timestamp — with no amount or account field. The actual crediting, including any lien/collateral account split, stays entirely the ledger's responsibility once Phase 3 exists. Logged the lien-account idea itself in the design doc's open questions (Section 7) instead of building it prematurely.
**What I'd do differently / what this taught me:** Before adding a money-shaped field to a non-ledger entity, check it against the ledger boundary in ADR 0004 first — "would this create a second place that claims to know where money went" is the concrete test, not just "does this field seem useful."
**Short version:** While designing the circle-rotation entities, I almost added an account/amount field to track payouts directly — then realized that would create a second, driftable record of money movement running in parallel to the ledger I'd already decided (ADR 0004) should be the single source of truth for that. I kept the rotation record as pure schedule metadata and left actual money movement to the ledger.

## @Transactional silently undid security side effects across most of AuthService

**Date:** 2026-08-14
**What I was trying to do:** First, verify the refresh token rotation and reuse-detection flow (ADR-0006) by running it end-to-end against the real app instead of just trusting the code and a passing compile. Later, wrote an automated Testcontainers-based integration suite covering the rest of the auth flow, including login lockout.
**What went wrong:** Manually, I found that reuse detection didn't actually revoke anything — a token that should have died on reuse was still usable afterward. I fixed that in `RefreshTokenService`/`AuthService.refresh()` and moved on. Once the automated test suite existed and exercised the lockout path (5 wrong passwords in a row), it turned out the exact same class of bug was also silently defeating account lockout: `failedLoginAttempts` reset to 1 on every single failed request instead of accumulating, so the account never actually locked no matter how many wrong passwords were tried.
**Why it happened:** The root cause is the same one in both places, and it's more pervasive than I first assumed: `login()`, `verifyEmail()`, and `loginWithGoogle()` all record something meant to survive a failure (a failed-attempt counter, an audit log entry, a stale-account deletion) and then throw an exception to signal that failure to the caller. Since all three methods are `@Transactional` with Spring's default rollback-on-any-RuntimeException behavior, every one of those intentional side effects was being silently undone the moment the signaling exception propagated. The refresh-token case was just the first instance I happened to test manually — the same shape of bug was quietly present everywhere else in the class too, and only surfaced once there was an automated test actually asserting on the *persisted* outcome of a failure path, not just its HTTP status code.
**How I fixed it:** Added `noRollbackFor` (naming the specific exceptions each method throws) to `login()`, `verifyEmail()`, and `loginWithGoogle()`, on top of the earlier fix to `RefreshTokenService.rotate()`/`AuthService.refresh()`.
**What I'd do differently / what this taught me:** A compiling, context-loading app proves wiring, not behavior — none of these four bugs were visible to either. The manual test caught one instance by luck (I happened to check the database after a reuse attempt); the automated suite caught the rest systematically, because it asserted on the actual persisted result (lockout after N attempts) rather than just the immediate response. Any method that logs/counts on a failure path and then throws needs its rollback rules checked explicitly — this is a pattern to grep for, not a one-off mistake.
**Short version:** Spring's default transaction rollback was silently undoing security-relevant side effects — refresh token family revocation, and separately, the failed-login counter that account lockout depends on — every time the method also threw an exception to report the failure to the caller. I caught the first instance by testing manually; writing an automated integration suite afterward surfaced that the same bug shape existed in two more places I hadn't manually exercised. Fixed all of them with `noRollbackFor` on the specific exceptions each method throws.

## A nullable foreign key still blocks deletes without ON DELETE SET NULL

**Date:** 2026-08-14
**What I was trying to do:** Get the "reclaim a stale unverified signup" behavior (documented in the previous entry above) passing under the new automated test suite — sign up twice with the same never-verified email and confirm the second attempt succeeds by deleting the first.
**What went wrong:** The second signup kept failing with a 409, even after I'd confirmed the reclaim logic itself was finding the right row and correctly deciding to delete it.
**Why it happened:** The first signup writes a `SIGNUP` audit log row referencing that user. `AuditLog.user` is a nullable column — by design, some events (like a failed login against an email that doesn't resolve to an account) never have a user to attach to — but nullable-in-the-entity doesn't mean nullable-at-delete-time: the foreign key constraint Hibernate generated by default has no `ON DELETE` clause, so Postgres refused to delete a `users` row that any `audit_log` row still pointed to, regardless of whether that column happened to allow NULL.
**How I fixed it:** Added `@OnDelete(action = OnDeleteAction.SET_NULL)` to `AuditLog.user`, which tells Hibernate to generate the constraint as `ON DELETE SET NULL` — deleting the user now orphans the audit row (`user` becomes `null`) instead of being blocked by it. Had to manually apply the equivalent `ALTER TABLE` to the local dev database too, since `ddl-auto: update` doesn't retrofit changes onto an existing constraint.
**What I'd do differently / what this taught me:** "Is this column nullable" and "can the row it references be deleted" are two different questions — a FK's delete behavior is a separate, explicit choice (`RESTRICT` by default, `SET NULL`, `CASCADE`) that has to match what the column's nullability already implies. If a field is nullable specifically to allow "this reference may not always exist," the FK should say so too.
**Short version:** A stale-signup cleanup feature kept failing for a reason that had nothing to do with its own logic — a foreign key from the audit log was blocking the delete, even though the referencing column was already nullable. The fix was making the database-level delete behavior (`ON DELETE SET NULL`) match the nullability the entity already declared, so an audit trail can outlive the account it was recorded against.

## A locked-accounts map only contains the IDs it actually finds

**Date:** 2026-08-25
**What I was trying to do:** Turn on Eclipse JDT's null analysis and see what it caught in `TransactionService`, expecting mostly noise from unannotated records and JPA entities.
**What went wrong:** Most of what it flagged was exactly that noise — method references like `Leg::accountId` warning about an unchecked conversion on their implicit `this`. But going through `postLedgerTransaction` line by line to judge which warnings were real turned up an actual gap that wasn't even one of the flagged lines: `LedgerDao.lockAccounts` runs `SELECT ... WHERE id IN (...)`, so it only puts an entry in the returned map for account IDs that actually matched a row. The balance-sufficiency check read straight from that map with `balances.get(leg.accountId())` and called `.compareTo(...)` on the result, assuming every leg's account ID would be present. Any leg referencing an account ID that didn't exist would have returned `null` there and thrown an NPE inside the transaction callback instead of a clear error.
**Why it happened:** Every current caller builds its `Leg`s from accounts already looked up through `requireUserAccount`, which does validate existence — so in practice the IDs passed to `lockAccounts` were always real. But nothing in `postLedgerTransaction` itself enforced that; it just assumed the map coming back would be as complete as the list going in.
**How I fixed it:** Added an explicit check right after `lockAccounts` — collect any requested account ID missing from the returned map and throw `AccountNotFoundException` before the balance check runs at all, so "does this account exist" and "is there enough balance" are two separate steps instead of one lookup doing both jobs.
**What I'd do differently / what this taught me:** A map built from a `WHERE ... IN (...)` query is only as complete as the rows that matched — treating its size as guaranteed equal to the input list is an assumption, not a fact, and it needs to be checked explicitly right before a transactional write, not inferred from "well, nothing calls it with a bad ID today."
**Short version:** JDT's null analysis mostly flagged framework-shaped noise on method references, but reviewing the flagged method to judge that turned up a real gap: `LedgerDao.lockAccounts` silently drops any account ID it can't find, and `postLedgerTransaction` assumed every ID would come back. Fixed by validating account existence explicitly before checking balances.

## Writing the ledger's test suite found a real modeling gap: clearing accounts can't have a balance floor

**Date:** 2026-08-25
**What I was trying to do:** Write Testcontainers-based tests proving the ledger's core guarantees actually hold — concurrent writes don't double-spend, idempotency replay doesn't reprocess, the net-zero and append-only triggers reject what they should. Needed a way to fund a test account with a starting balance to exercise any of this.
**What went wrong:** Funding a test account through the real `postDeposit` path (rather than writing the balance column directly, so the cached balance and the ledger's own aggregate would agree from the start) failed immediately with `InsufficientBalanceException` — on every single test, before any of the actual logic under test even ran.
**Why it happened:** `postDeposit` debits the platform's `CLEARING_STRIPE`/`CLEARING_PAYPAL` system accounts, which are seeded at $0. The balance-sufficiency check treated every account uniformly, so debiting a clearing account with nothing in it failed the same way debiting an underfunded user account would. But a clearing account isn't a spending account — its whole purpose is tracking net external inflow, and it's *supposed* to run negative every time real money flows in from Stripe or PayPal. The uniform check was actually a modeling bug that had been sitting there the whole time; it just took a test that genuinely exercised the deposit path (rather than a backdoor SQL update) to surface it.
**How I fixed it:** Rather than passing "this specific account is exempt" as a parameter at each call site — which only protects the exemption if every future caller remembers to declare it — made the exemption structural: `LedgerDao.lockAccounts` now determines "unlimited" from the account's own type (`user_account_type LIKE 'CLEARING_%'`), so a future funding source needs zero code changes here as long as it follows the naming convention already in place. Checked whether any *other* account type had the same problem first: `LIEN_SEIZURE` already caps itself at `lienBalance.min(groupLoss)`, and anything the seizure doesn't cover goes to the buffer and group-shortfall steps rather than ever pushing a member's own account negative — that's the actual point of the default waterfall design, not something this fix needed to touch.
**What I'd do differently / what this taught me:** Funding test fixtures through the real write path instead of a raw SQL backdoor is what actually found this — a backdoor fixture would have hidden the bug indefinitely, since nothing would ever have called `postDeposit` for real. And the general lesson on the fix itself: a business rule like "this account is allowed to go negative" belongs on the thing it's actually true of (the account's type), not repeated as a parameter at every place that might debit it.
**Short version:** Writing tests that funded accounts through the real `postDeposit` path (instead of a raw SQL shortcut) immediately found that deposits were completely broken — the platform's own clearing accounts start at $0, but the balance check didn't know they're supposed to run negative. Fixed by making "can this account go negative" a structural property of the account's type rather than something declared per call-site, so it can't be forgotten for a future funding source.

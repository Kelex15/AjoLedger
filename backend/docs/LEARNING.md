# AjoLedger — Learning Log

Concepts worth understanding deeply, not just using, as they come up while building this.

## Spring Framework 7 API Versioning

**Where it shows up:** `backend/src/main/java/com/ajoledger/backend/system/WebConfig.java`, and the `version` attribute on `UserController`'s mappings.
**Why it matters here:** This is the actual mechanism behind ADR 0001 — how the API can evolve across versions without breaking existing clients or baking a version number into every resource URL.
**What to actually learn (not just use):** Not just "call `useRequestHeader(...)` on a configurer" — understand how `ApiVersionStrategy` resolves a version from a request (header, path segment, query param, or media-type parameter — all pluggable), how it parses/compares versions (`SemanticVersionParser` by default), how it picks the matching handler method when multiple `version` values are declared for the same path, and how `ApiVersionDeprecationHandler` can emit RFC 9745/8594 `Deprecation`/`Sunset`/`Link` headers automatically when a version is marked deprecated.
**Where to start:** The official Spring Framework reference docs' "API Version" page (docs.spring.io, Web MVC → MVC Config section) is the primary source — this is a genuinely new (2025) feature, so any blog post about it is worth checking against that page rather than trusting on its own.
**You should know:** "How would you version a REST API without breaking existing clients?" — being able to compare URL-prefix vs. header vs. media-type strategies, and explain *why* a resource's URL shouldn't encode its protocol version, is the real question behind "how did you do versioning."

## Spring's @Transactional rollback rules

**Where it shows up:** `RefreshTokenService.rotate()`, and `AuthService.refresh()`/`login()`/`verifyEmail()`/`loginWithGoogle()` — the Challenges log entry on this covers all four.
**Why it matters here:** The whole point of catching a security-relevant exception (a reused refresh token, a wrong password, an expired verification link) is often to record that something happened — revoke a token family, increment a failed-attempt counter, write an audit log, delete a stale row — *before* propagating the error. Spring's default rollback behavior actively fights that unless told not to, and it turned out to be fighting it in four different methods, not just the one I happened to test manually first.
**What to actually learn (not just use):** Not just "add `noRollbackFor`" — understand that `@Transactional`'s default is to roll back on any unchecked exception (and never on checked exceptions, unless configured otherwise), that this rule is evaluated independently at *every* transactional proxy boundary an exception passes through, not just where it's thrown, and that with the default `REQUIRED` propagation, nested `@Transactional` calls share one physical transaction — so a rollback decision made anywhere in that chain wins. `noRollbackFor`/`rollbackFor` override the default per exception type, per method. And the practical lesson: any method that logs, counts, or deletes on a failure path and then throws is a candidate for this bug — worth checking every one of them, not just the first you find.
**Where to start:** The official Spring Framework reference docs, Data Access section, "Declarative transaction management" — specifically the subsections on rollback rules and transaction propagation. Worth reading before reaching for `noRollbackFor` as a reflexive fix.
**You should know:** "Have you ever had a transaction roll back something you didn't expect?" — this is a concrete, real answer: a caught-and-logged exception that was supposed to leave a security action in place, silently undone by the default rollback rule — and finding it in one place was a sign to go check for the same shape of bug everywhere else in the class.

## JPA foreign key delete behavior vs. column nullability

**Where it shows up:** `AuditLog.user` — the stale-signup reclaim fix in the Challenges log.
**Why it matters here:** A column being nullable in the entity (and in the schema) doesn't mean the database will let you delete the row it's currently pointing to. Those are two separate questions, and JPA's default `@ManyToOne` mapping only answers the first one.
**What to actually learn (not just use):** By default, Hibernate generates a foreign key with no `ON DELETE` clause, which means the database's default (`RESTRICT`/`NO ACTION`) applies — deleting the referenced row fails if anything still points to it, regardless of whether that pointing column is nullable. Hibernate's `@OnDelete(action = OnDeleteAction.SET_NULL)` (or `CASCADE`) is a separate, explicit annotation that changes what SQL actually gets generated for the constraint. The right choice depends on what the nullability was *for* — if a column is nullable specifically because "this reference might legitimately not exist," `SET NULL` usually matches that intent; `CASCADE` is for genuine ownership (the child row has no reason to exist without the parent).
**Where to start:** Hibernate's own reference docs on `@OnDelete`, plus Postgres's docs on `FOREIGN KEY ... ON DELETE` actions — worth understanding the database-level behavior independently of the ORM annotation, since the annotation is just generating that SQL for you.
**You should know:** "Tell me about a time a delete failed unexpectedly" — a real one: a cleanup feature failed not because of its own logic, but because a related table's foreign key had no `ON DELETE` behavior specified, even though the column itself was already nullable.

## Postgres constraint triggers can't use transition tables

**Where it shows up:** `backend/src/main/resources/db/migration/V3__create_ledger_tables.sql` — the net-zero balance check on `ledger_entry`.
**Why it matters here:** The ledger's core invariant — every transaction's debit and credit legs must net to zero — can only be checked once all of a transaction's legs exist, not as each individual leg is inserted. A *deferred* constraint trigger (fires at commit, not per-statement) is the right tool for that. The first attempt paired it with a transition table (`REFERENCING NEW TABLE AS ...`) to see every newly-inserted row in one pass — Postgres's usual answer to "give me every row this statement just touched."
**What to actually learn (not just use):** `REFERENCING` (transition tables) and `CONSTRAINT TRIGGER` are mutually exclusive in Postgres — `CREATE CONSTRAINT TRIGGER ... REFERENCING ...` is rejected outright, no clause ordering fixes it. Transition tables only exist on plain, non-deferrable triggers. This isn't just a syntax restriction, it wouldn't have worked conceptually either: a transition table reflects exactly the rows one SQL statement touched, but the entire value of a *deferred* trigger is decoupling "when this fires" from "which statement wrote the data" — by commit time, several separate `INSERT` statements may have each contributed one leg, and a transition table scoped to a single statement couldn't see the others regardless. The fix: a `FOR EACH ROW` deferred constraint trigger whose function ignores the transition data entirely and just queries the real table for `NEW.transaction_id` — since every earlier statement in the transaction has already applied by commit time, that query correctly sees the complete set of legs no matter how many statements produced them (read-your-own-writes within a transaction).
**Where to start:** Postgres's own `CREATE TRIGGER` reference page — the syntax diagram scopes `REFERENCING` out of constraint triggers directly, and the "Transition Tables" subsection explains why. Reading the grammar settles this faster than searching for the error message, since it isn't really documented as a gotcha — it's just implicit in the syntax.
**You should know:** "How do you enforce a multi-row invariant across an entire transaction, at commit time, in Postgres?" — deferred constraint triggers are the mechanism, but the instinct to reach for transition tables to see "everything this transaction wrote" doesn't work with them. Querying the real table from inside a `FOR EACH ROW` deferred trigger is the actual pattern, and it works specifically because of same-transaction read visibility, not because of anything the trigger framework hands you directly.

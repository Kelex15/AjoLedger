# AjoLedger: Learning Log

Concepts worth understanding deeply, not just using, as they come up while building this.

## A fixed-shape transfer primitive, plus a separate operation layer for business grouping

**Where it shows up:** `LedgerTransaction`/`Leg` (always exactly one debit, one credit) and `LedgerOperation` (groups several `LedgerTransaction`s under one business event, e.g. a payout's net transfer, buffer fee, and lien skim).
**Why it matters here:** `postPayout` used to post one transaction with a debit and up to three credits. That's completely valid double-entry accounting on its own, a compound journal entry with more than two lines isn't wrong, and this codebase's own deferred Postgres trigger already validates that legs sum to zero regardless of how many there are, so the split isn't buying any extra correctness there. What it does buy: a transaction record that's always exactly two accounts means reading one back (an API response, an audit log line) never has to ask "which of these several credits was the real destination." A `List<Leg>` transaction can express that ambiguity; a `transfer(from, to, amount)`-shaped one structurally can't. `LedgerOperation` is what recovers the fact that several such transfers came from one business action, without pushing variable arity back into the transaction primitive to do it.
**What to actually learn (not just use):** Three separate ideas were getting conflated in one record: an entry (one account's impact), a transaction (one movement between two accounts), and an operation (one business action that caused several movements). Once separated, the ledger's own primitive only ever has to understand `transfer(from, to, amount)`, not what a payout or a fee is, which makes it genuinely reusable across every future money-moving feature without the primitive itself growing new shapes. Atomicity doesn't get lost in the split: several logical `LedgerTransaction`s still commit inside one physical database transaction inside one `LedgerOperation`, so "three ledger transactions" doesn't mean three independent commits. The operation id also pays for itself later, in reconciliation and support tooling, by letting every transaction it caused be pulled back up as one event.
**Where to start:** "Aggregate" and "aggregate root" in Eric Evans' Domain-Driven Design is the closest formal treatment of one thing coordinating several simpler things without those simpler things themselves growing a variable shape. Comparing a compound journal entry (traditional accounting) against this split-plus-correlation-id approach directly clarifies that the split is a read-side/API ergonomics choice, not an accounting requirement, and not a correctness fix either since the database enforces balance either way.
**You should know:** "Why not just let one transaction have as many legs as the event needs?" It's a legitimate, DB-enforced-either-way accounting model. The honest answer isn't "it's wrong," it's that a fixed two-leg primitive stays simple and unambiguous to read back as more transaction types get added, and the grouping a compound event needs is better served by an explicit id one layer up than by variable arity on the primitive itself.

## Hibernate's persistence-context identity map hides raw-JDBC writes

**Where it shows up:** `CircleService.joinCircle`/`resolveRoundIfComplete`, the `CircleAccount` (pot) balance read at payout time.
**Why it matters here:** ADR-0004 splits this system's account layer in two: JPA for entity reads, raw `JdbcTemplate` for every balance-affecting ledger write. That split assumes a JPA-loaded account's `balance` field is safe to trust. It isn't, within a single transaction, once a raw-JDBC write to that same row has happened in between.
**What to actually learn (not just use):** A JPA persistence context (Hibernate `Session`) guarantees object identity: every query for the same entity id within one transaction returns the *same* Java object instance, not a fresh one re-hydrated from the latest row. This holds even for a derived/JPQL query, not just `find()` by id. Hibernate still executes the SQL, but then discards the freshly-read column values in favor of whatever the already-managed instance already holds in memory. A raw JDBC `UPDATE` (like this ledger's balance writes) never touches that in-memory state at all, so any entity loaded before such a write, and read again after it within the same transaction, silently returns stale data, with no error and nothing to indicate the read is wrong.
**Where to start:** Hibernate's reference docs on the persistence context / first-level cache explain the identity-map guarantee directly. The practical fix in this codebase was reading the true balance straight from `ledger_entry` (`LedgerDao.getBalance`, already built for verification purposes) instead of the cached entity field, anywhere a balance is read mid-transaction after an earlier write.
**You should know:** "Have you seen a case where an ORM's caching caused a wrong read, not just a wrong write?" This is a concrete one: a JPA entity loaded early in a transaction (to get its id) silently going stale the moment a raw-SQL write to that same row happens later in the same transaction, with the ORM never re-checking.

## Laplace smoothing for ranking small-sample ratios

**Where it shows up:** `CircleService.computeReputationScore` (the `successRate` term).
**Why it matters here:** A raw success/failure ratio breaks down for small samples: a member with 1 success and 0 failures ranks as more reliable (1.0) than one with 20 successes and 1 withdrawal (≈0.95), even though the second member has far more evidence behind their record. Comparing proportions from wildly different sample sizes needs a correction, not a raw ratio.
**What to actually learn (not just use):** Laplace smoothing (add-k smoothing) adds a small assumed prior count to both the success and failure sides before computing the ratio, so a thin track record gets pulled toward a neutral baseline instead of swinging on one data point, while a large sample's real rate dominates once it's built up enough evidence. It's the simpler cousin of more rigorous tools for the same problem, like a Wilson score interval (the method behind e.g. Reddit's comment ranking). Laplace smoothing trades some statistical rigor for a one-line formula that's easy to explain.
**Where to start:** "Additive smoothing" on Wikipedia covers the general technique. Comparing it side-by-side with a Wilson score interval clarifies why both exist and when the more rigorous one earns its complexity.
**You should know:** "How would you rank things by a success rate when some have way more data behind them than others?" A naive ratio lets a small sample masquerade as certainty. Smoothing (or a confidence-interval-based method) fixes that by making the ratio itself account for how much evidence backs it.

## Spring Framework 7 API Versioning

**Where it shows up:** `backend/src/main/java/com/ajoledger/backend/system/WebConfig.java`, and the `version` attribute on `UserController`'s mappings.
**Why it matters here:** This is the actual mechanism behind ADR 0001: how the API can evolve across versions without breaking existing clients or baking a version number into every resource URL.
**What to actually learn (not just use):** Not just "call `useRequestHeader(...)` on a configurer": understand how `ApiVersionStrategy` resolves a version from a request (header, path segment, query param, or media-type parameter, all pluggable), how it parses/compares versions (`SemanticVersionParser` by default), how it picks the matching handler method when multiple `version` values are declared for the same path, and how `ApiVersionDeprecationHandler` can emit RFC 9745/8594 `Deprecation`/`Sunset`/`Link` headers automatically when a version is marked deprecated.
**Where to start:** The official Spring Framework reference docs' "API Version" page (docs.spring.io, Web MVC → MVC Config section) is the primary source. This is a genuinely new (2025) feature, so any blog post about it is worth checking against that page rather than trusting on its own.
**You should know:** "How would you version a REST API without breaking existing clients?" Being able to compare URL-prefix vs. header vs. media-type strategies, and explain *why* a resource's URL shouldn't encode its protocol version, is the real question behind "how did you do versioning."

## Spring's @Transactional rollback rules

**Where it shows up:** `RefreshTokenService.rotate()`, and `AuthService.refresh()`/`login()`/`verifyEmail()`/`loginWithGoogle()`. The Challenges log entry on this covers all four.
**Why it matters here:** The whole point of catching a security-relevant exception (a reused refresh token, a wrong password, an expired verification link) is often to record that something happened (revoke a token family, increment a failed-attempt counter, write an audit log, delete a stale row) *before* propagating the error. Spring's default rollback behavior actively fights that unless told not to, and it turned out to be fighting it in four different methods, not just the one I happened to test manually first.
**What to actually learn (not just use):** Not just "add `noRollbackFor`": understand that `@Transactional`'s default is to roll back on any unchecked exception (and never on checked exceptions, unless configured otherwise), that this rule is evaluated independently at *every* transactional proxy boundary an exception passes through, not just where it's thrown, and that with the default `REQUIRED` propagation, nested `@Transactional` calls share one physical transaction, so a rollback decision made anywhere in that chain wins. `noRollbackFor`/`rollbackFor` override the default per exception type, per method. And the practical lesson: any method that logs, counts, or deletes on a failure path and then throws is a candidate for this bug, and it's worth checking every one of them, not just the first you find.
**Where to start:** The official Spring Framework reference docs, Data Access section, "Declarative transaction management", specifically the subsections on rollback rules and transaction propagation. Worth reading before reaching for `noRollbackFor` as a reflexive fix.
**You should know:** "Have you ever had a transaction roll back something you didn't expect?" This is a concrete, real answer: a caught-and-logged exception that was supposed to leave a security action in place, silently undone by the default rollback rule. And finding it in one place was a sign to go check for the same shape of bug everywhere else in the class.

## JPA foreign key delete behavior vs. column nullability

**Where it shows up:** `AuditLog.user` (the stale-signup reclaim fix in the Challenges log).
**Why it matters here:** A column being nullable in the entity (and in the schema) doesn't mean the database will let you delete the row it's currently pointing to. Those are two separate questions, and JPA's default `@ManyToOne` mapping only answers the first one.
**What to actually learn (not just use):** By default, Hibernate generates a foreign key with no `ON DELETE` clause, which means the database's default (`RESTRICT`/`NO ACTION`) applies. Deleting the referenced row fails if anything still points to it, regardless of whether that pointing column is nullable. Hibernate's `@OnDelete(action = OnDeleteAction.SET_NULL)` (or `CASCADE`) is a separate, explicit annotation that changes what SQL actually gets generated for the constraint. The right choice depends on what the nullability was *for*. If a column is nullable specifically because "this reference might legitimately not exist," `SET NULL` usually matches that intent; `CASCADE` is for genuine ownership (the child row has no reason to exist without the parent).
**Where to start:** Hibernate's own reference docs on `@OnDelete`, plus Postgres's docs on `FOREIGN KEY ... ON DELETE` actions. It's worth understanding the database-level behavior independently of the ORM annotation, since the annotation is just generating that SQL for you.
**You should know:** "Tell me about a time a delete failed unexpectedly." A real one: a cleanup feature failed not because of its own logic, but because a related table's foreign key had no `ON DELETE` behavior specified, even though the column itself was already nullable.

## Postgres constraint triggers can't use transition tables

**Where it shows up:** `backend/src/main/resources/db/migration/V3__create_ledger_tables.sql` (the net-zero balance check on `ledger_entry`).
**Why it matters here:** The ledger's core invariant (every transaction's debit and credit legs must net to zero) can only be checked once all of a transaction's legs exist, not as each individual leg is inserted. A *deferred* constraint trigger (fires at commit, not per-statement) is the right tool for that. The first attempt paired it with a transition table (`REFERENCING NEW TABLE AS ...`) to see every newly-inserted row in one pass, which is Postgres's usual answer to "give me every row this statement just touched."
**What to actually learn (not just use):** `REFERENCING` (transition tables) and `CONSTRAINT TRIGGER` are mutually exclusive in Postgres. `CREATE CONSTRAINT TRIGGER ... REFERENCING ...` is rejected outright, and no clause ordering fixes it. Transition tables only exist on plain, non-deferrable triggers. This isn't just a syntax restriction, it wouldn't have worked conceptually either: a transition table reflects exactly the rows one SQL statement touched, but the entire value of a *deferred* trigger is decoupling "when this fires" from "which statement wrote the data." By commit time, several separate `INSERT` statements may have each contributed one leg, and a transition table scoped to a single statement couldn't see the others regardless. The fix: a `FOR EACH ROW` deferred constraint trigger whose function ignores the transition data entirely and just queries the real table for `NEW.transaction_id`. Since every earlier statement in the transaction has already applied by commit time, that query correctly sees the complete set of legs no matter how many statements produced them (read-your-own-writes within a transaction).
**Where to start:** Postgres's own `CREATE TRIGGER` reference page. The syntax diagram scopes `REFERENCING` out of constraint triggers directly, and the "Transition Tables" subsection explains why. Reading the grammar settles this faster than searching for the error message, since it isn't really documented as a gotcha; it's just implicit in the syntax.
**You should know:** "How do you enforce a multi-row invariant across an entire transaction, at commit time, in Postgres?" Deferred constraint triggers are the mechanism, but the instinct to reach for transition tables to see "everything this transaction wrote" doesn't work with them. Querying the real table from inside a `FOR EACH ROW` deferred trigger is the actual pattern, and it works specifically because of same-transaction read visibility, not because of anything the trigger framework hands you directly.

## Eclipse JDT null analysis: what it actually flags, and where to suppress

**Where it shows up:** `TransactionService.postLedgerTransaction` (`Leg::accountId`), `FixedSizeCircleSizingPolicy.canMemberJoin` (`CircleMembership::getStatus`).
**Why it matters here:** Turning on JDT's null analysis immediately warned on ordinary method references over private records and JPA entities, not on anything resembling the actual bug in `LedgerDao.lockAccounts` (see the Challenges log entry). The easy reaction is to rewrite every flagged method reference back into a lambda until the warnings stop, but that trades away idiomatic code for quieter tooling without fixing anything real.
**What to actually learn (not just use):** JDT's null analysis doesn't have built-in nullness knowledge of the whole JDK. It isn't the reason `Map.get()`'s possible `null` gets flagged (it doesn't, here). What it does flag is annotation-based: a method reference's implicit `this` needing to conform to `@Nonnull` when the receiver's type (a record, a Lombok-generated entity) carries no null annotations of its own. That's a limitation of the static check on unannotated types, not evidence of a real defect. `@SuppressWarnings("null")` doesn't have to go on the whole method either; placed directly on a local variable declaration, it silences only that statement, leaving the rest of the method under full analysis. That matters most in a method with real transactional consequences, where blanket-suppressing to quiet two harmless warnings would also hide a genuine one later.
**Where to start:** Eclipse's Java Compiler → Errors/Warnings → Null Analysis preferences page explains the annotation-based vs. flow-based distinction directly; worth reading before treating every warning the same way.
**You should know:** "When is a static analysis warning safe to suppress, and how narrowly should you scope that?" The real answer here was two-part: scope the suppression to the exact declaration causing it, not the enclosing method, especially in code that moves money; and treat a flagged method as a prompt to actually read the surrounding logic rather than reflexively silencing or rewriting it. That's how the real `lockAccounts` gap got found, on a line the analyzer never flagged at all.

## A shared lock's cost tracks the volume through it, not how many things share it

**Where it shows up:** The ledger hash chain's write path (ADR-0010): a synchronous per-insert trigger first, then a rejected "split into per-table locks" fix, then the async batch-sealing design that actually shipped.
**Why it matters here:** A trigger hashing every `ledger_operation`/`transaction`/`ledger_entry` row at insert time, chained through one shared lock, measured at roughly 500-1,200 tps regardless of concurrency, versus 9,700+ tps unhashed. The first fix I reached for was intuition, not measurement: three independent per-table locks "should" let unrelated writes proceed in parallel, so I estimated roughly 3x. Actually benchmarking it, using a workload matching this system's real ratio of one `transaction` row to two `ledger_entry` legs per event, showed almost no improvement, and slightly worse at high concurrency.
**What to actually learn (not just use):** A shared lock's throughput ceiling is set by whichever table dominates the write volume passing through it, not by how many tables happen to share the lock. `ledger_entry` always has twice the row count of `transaction` here, since every transaction is exactly two legs, so it alone accounts for most of the serialized work whether the lock is global or scoped per table. Splitting a bottleneck into more locks only helps if the load was actually spread evenly across what got split; if one component already dominates, splitting just renames the bottleneck without shrinking it. The fix that actually worked didn't repartition the lock at all, it moved the hashing off the synchronous write path entirely into a periodic batch job, so the lock gets acquired once per sealing interval instead of once per row.
**Where to start:** Amdahl's law is the formal version of this: the speedup available from parallelizing part of a system is bounded by the fraction of the system's total work that part represents, not by how many parallel lanes get added to it. The actual numbers here came from a real benchmark against a throwaway database, not a formula, which is itself the lesson: a plausible-sounding estimate turned out to be simply wrong once measured.
**You should know:** "Why didn't splitting the lock per table help?" is worth being able to answer precisely: the write volume wasn't distributed the way the fix assumed. Two of every three rows a real event produces are `ledger_entry` rows, so an independent lock on that one table alone had to serialize nearly the same volume the shared lock already did.

# AjoLedger — Trust & Risk Model (Design Doc)

**File location:** `backend/docs/design/v3.md`

**Status:** Accepted — supersedes `v2.md`. Sections 3–5 reflect what's actually implemented as of 2026-09-07; Section 7 still flags genuinely open design questions, including the ones this version couldn't resolve.

## Versioning scheme

Each **major version** of the trust/risk model lives in its own file: `backend/docs/design/v1.md`, `v2.md`, etc. When the model's actual rules change significantly (not implementation details, but things like the collateral formula, the waterfall order, what counts as a default, how reserve accrues, new account types), a new version file is created, forked from the latest one and updated for the new rules. Prior version files are never edited once superseded; they stay as the honest historical record of how the design evolved and why.

**Within a version file**, minor revisions (clarifications, non-breaking architecture additions, fixes to how a rule is *implemented* without changing what the rule *is*) are tracked with a lightweight changelog at the top of that file, using a `vX.0`, `vX.1`, etc. numbering — no new file needed for these.

Loopholes found post-launch or during implementation belong in that version's changelog (or trigger a new version file if the fix changes an actual rule) — `backend/docs/CHALLENGES.md` can capture the debugging story alongside it, but the latest version file is the source of truth for what the model *is* right now.

## 1. Background

I'm building a digital platform for rotating savings and credit associations (known as Ajo/Esusu/Susu/Chama/tandas/etc. depending on region) — a group of members each contribute a fixed amount on a fixed schedule, and the full pot rotates to a different member each round until everyone has been paid once.

The core engineering challenge isn't the accounting (double-entry bookkeeping is well understood) — it's that traditional versions of this rely on **social trust** to prevent someone from taking their payout early and then abandoning the group before contributing their fair share. A digital platform, especially one meant to work between people who don't already know each other, has to replace that social trust with something structural.

## 1.5 Scope: banking foundation vs. rotational savings focus

This project is **not** a general-purpose banking system — it's a rotational savings platform that happens to need a minimal banking layer underneath it to function correctly. Effort should be weighted accordingly:

**Banking foundation (lighter build, exists only to support the layer above):**
- Standard accounts and balances, deposit/withdraw
- A double-entry transaction ledger — every movement debits one account and credits another, and the books always reconcile
- Idempotency on all money-moving operations, so a retried request can't be processed twice
- Enough rigor that the rotational savings logic has something correct to build on — but no more than that. There's no need for features a real bank would need (multi-currency, interest-bearing accounts, external payment rails, etc.) unless they end up serving the circle mechanics directly.

**Rotational savings (the actual focus, most of the build effort and the differentiating engineering):**
- Circle creation, membership, and contribution scheduling
- The collateral formula and payout eligibility (Section 4)
- The lien: reserve accrual and collateral, unified (Section 3.2)
- The shared insurance buffer (Section 3.3)
- The default waterfall (Section 5)
- Composition control — letting a circle creator hand-pick membership to reduce correlated default risk (still being explored, Section 7)

This split matters for how the project gets pitched and built: the banking layer is a means to an end, not the story. The trust/risk model is where the genuine, non-textbook design decisions live, and it's what should dominate both build time and the eventual README.

## 2. The core problem

Once a member receives their payout, nothing stops them from ceasing further contributions and leaving the remaining members short. This is a well-known structural weakness of ROSCAs, not a bug introduced by digitizing them — it's an adverse-selection/moral-hazard problem: whoever is earliest in the payout rotation has the least ongoing incentive to keep contributing honestly.

### Rejected approach: ordering alone
I initially considered scheduling new/unproven members later in the rotation, so by the time they're paid, they've already demonstrated reliability. This helps, but does **not** fully solve the problem — it breaks down at the minimum group size. In a 2-person circle, someone has to go first, and there is no way to sequence around that; ordering can reduce exposure in larger groups but cannot eliminate first-mover risk in general.

### Rejected approach: reputation as a plain score
I also considered a "trust score" that grows with completed circles and gates eligibility for early payout slots. I ruled this out because a score with no money behind it doesn't actually cover a loss — if a highly-trusted member defaults, there's nothing real to claw back. Reputation has to be backed by actual funds to mean anything financially.

## 3. The model (current version)

Three account types work together to cover risk in layers:

### 3.1 Personal balance
Standard member funds — contributions in, payouts out, nothing unusual.

### 3.2 The lien: reserve and collateral, unified
v1 treated "personal reserve" (built from withheld payout shares) and "collateral hold" (posted up front for an early slot) as two conceptually separate things. They're actually the same money doing the same job at different times, so they're now one account: `LIEN`.

- **How it grows:** every payout a member receives withholds a slice into their own `LIEN`, immediately — not deferred until they finish the circle (see Section 6.3's worked example). If they later default, that balance is already sitting there to be seized.
- **How it's used:** a member taking an early (riskier) payout position can also voluntarily top up their `LIEN` from their own funds if the balance they've already accrued doesn't cover the collateral formula (Section 4) for that slot.
- **One pooled balance, not per-circle.** Whatever's in a member's `LIEN` can back a collateral requirement in *any* future circle, not just the one it was earned in.
- **Not released per-circle.** It stays locked as long as the member has any active circle membership requiring ongoing contribution. It only becomes withdrawable once none does — that's what "completes a circle successfully" in the v1 wording actually meant: not when the money is *withheld*, but when it becomes *theirs to take back out*.
- **Pooled across time, not across concurrent circles.** A member can only ever be an active member of one circle at a time (Section 7), so in practice `LIEN` never has to cover more than one circle's exposure at once. It still carries forward between circles, since it isn't released until the current one finishes.

### 3.3 Shared insurance buffer (platform-wide, pooled)
- Funded by a small fee skimmed from every money-moving event across every circle on the platform, not just one circle — both when a member contributes into a pot (e.g. ~1%) and when a member receives a payout (e.g. ~2%). Rates are tunable, not fixed by this doc.
- Owned by no individual member — exists to absorb losses that a defaulting member's own `LIEN` can't fully cover.
- Necessary because: (a) brand-new members have zero `LIEN` balance, and (b) even an established member's balance may be smaller than the loss they cause.

## 4. Collateral formula

For any member taking an early (riskier) payout position:

```
Potential group loss = contribution amount × (total rounds − payout position)
Required collateral = max(0, Potential group loss − member's banked LIEN balance)
```

A member paid out in position P of N total rounds still owes a contribution for every round after their own payout — that's `N − P` rounds. That's the exposure the group carries if they vanish right after being paid, and it's exactly what the collateral formula sizes against. Position 1 (earliest) faces the largest exposure; the very last position needs no collateral at all, since by the time they're paid, every round — including their own — has already been contributed to.

- A brand-new member (zero `LIEN`) taking an early slot pays full collateral in real cash, or takes a late slot instead (which requires no collateral).
- An established member with enough banked `LIEN` can take an early slot with **zero new cash**, because their existing balance already covers the formula.
- This unifies "deposit" and "reputation" into one mechanism instead of two competing ones — deposits shrink to zero over time as real (imperfect, money-backed) trust accumulates.

## 4.5 Reputation score and position assignment

Positions are assigned at circle lock, not at join, so every candidate can be scored on equal footing. Higher reputation gets the earlier (riskier, more valuable) position — it rewards proven reliability with something people actually want, and it lines up with 4's own logic, since a high-reputation member plausibly already has enough banked `LIEN` to cover an early slot without new cash.

```
successRate = (successes + prior) / (successes + prior + penalizedFailures + prior)
lienCoverageRatio = min(1, LIEN balance / (contribution amount × (total rounds − 1)))
reputationScore = w × successRate + (1 − w) × lienCoverageRatio
```

- `successes`/`penalizedFailures` are lifetime counts of a member's completed vs. withdrawn/defaulted circle memberships, across every circle they've ever been in, not scoped to the one being formed.
- A default counts 3× a withdrawal toward `penalizedFailures`, since a default causes real financial harm to the group and a withdrawal doesn't.
- `prior` (Laplace smoothing) keeps a brand-new member with no history at a neutral 0.5 instead of an undefined or wildly swingy ratio off one data point.
- `lienCoverageRatio`'s denominator is exactly Section 4's "potential group loss" at position 1, the worst case — the same formula, reused rather than a new one invented.
- `w = 0.5` and the 3× default multiplier are both tunable placeholders, not tuned.
- Ties (two members landing on the same score, most commonly two brand-new members) break by join order, so the sort stays deterministic.

## 5. Default waterfall

When a member defaults after receiving a payout, losses are absorbed in this order:

1. **Their own `LIEN` balance** is seized first, capped at the group loss amount.
2. **The shared insurance buffer** covers whatever the lien didn't — up to whatever the buffer currently holds. It isn't required to fully cover the remainder; if it can't, whatever's left goes to step 3.
3. **Remaining group members absorb any final shortfall** — expected to be rare if collateral is sized correctly.

What steps 1 and 2 recover doesn't land in the pot directly. It's credited to a per-circle reserve account, then released into the pot in an even share at each of the circle's remaining rounds, rather than as a lump sum on whichever round happens to resolve next. A recovered default is the whole group's loss to begin with, so its recovery belongs to the group as a whole, not to whichever member's payout falls next. The release amount recalculates from the reserve's current balance and rounds still ahead each time, so a second default before the first has fully released just folds into the same schedule.

**Step 3 is resolved: it's never a forced transfer.** Nothing is ever debited from a remaining member's own account to cover what steps 1 and 2 couldn't recover — that was ruled out as its own risk (a member who can't afford an assessment now defaults too, the exact correlated-failure pattern the whole model exists to avoid). Instead, whatever fraction of the loss *was* recovered spreads evenly across the circle's remaining rounds via the reserve mechanism above; whatever wasn't recovered simply means every remaining round's payout is proportionally smaller for the rest of the circle's life. Not a lump loss landing on one round, and not a bill sent to anyone.

## 6. Worked examples

### 6.1 Two brand-new users, 2-person circle
Neither has a `LIEN` balance yet (first circle for both). Ordering alone can't protect the group, since someone must go first. Whoever takes the early slot pays full collateral (real cash) sized to the group's exposure; the other member, taking the guaranteed-safe late slot, pays nothing.

### 6.2 Established member defaults
Chinedu has a `LIEN` balance of $150 from prior completed circles. He takes an early slot in a new circle without paying new cash, since his balance covers the collateral requirement. He later defaults with 3 rounds still remaining after his own payout, on a $100/round circle — group loss = $100 × 3 = $300.
- Step 1: His $150 `LIEN` is seized, covering half.
- Step 2: The shared buffer covers the remaining $150.
- Step 3: No shortfall reaches the other members.

### 6.3 Lien accrual mechanic
A member's payout doesn't arrive in full — a slice is withheld into their own `LIEN` on *every* payout, not just once a circle completes, and a smaller slice funds the shared buffer at the same time. Illustrative rates: a $400 payout nets $332 to the member's spendable balance, with $60 (15%) into their `LIEN` and $8 (2%) into the shared buffer. The `LIEN` portion accumulates across circles over time, reducing (eventually to zero) the cash collateral needed for future early slots — but it isn't touchable while any active circle membership still requires it; withdrawal only opens up once none does.

## 7. Known open questions / not yet resolved
These are flagged honestly as unresolved:

- **Resolved: group absorption (waterfall step 3)** never forces a transfer from remaining members. See Section 5.
- **Resolved: a member can only be an active member of one circle at a time.** This closes the "join many small circles to accrue `LIEN`, then exploit a larger one" gaming concern directly, since there's no concurrent exposure to exploit. It's also what makes `LIEN`'s pooling (Section 3.2) safe to reason about without summing exposure across circles.
- **Resolved: reputation-based position assignment.** See Section 4.5.
- **Not yet built: need-based `LIEN` seize/release.** `postPayout` currently skims a flat rate into `LIEN` regardless of how much a member already has banked relative to their remaining exposure. The intended replacement ties the skim, and a matching gradual release back to spendable balance as remaining exposure shrinks with each successful contribution, to the same collateral formula already governing early-slot eligibility (Section 4), evaluated continuously against *current* round rather than fixed payout position.
- What's the platform's exposure if the shared buffer itself runs low during a period of unusually many defaults (e.g. a broader economic shock hitting many members' circles at once)?
- Is there a risk that requiring collateral from new members defeats the core purpose of the product (serving people without spare capital)? Worth user-testing the last-position-only, zero-collateral path as the default onboarding experience.
- **Gated (invite-only) circles**, as a second, independent trust lever alongside everything above: letting a creator hand-pick membership to reduce the odds of *correlated* defaults (several members going bad in the same circle at once, which is when the waterfall actually gets stressed), and relaxing the collateral formula's parameters for such a circle since a handpicked group carries real information the platform doesn't otherwise have. Sketched direction: one-time, targeted invite codes (by username for existing users, or by email for people not yet onboarded), granting eligibility to call `joinCircle` rather than membership itself — a funded contribution is still the only thing that truly completes joining. Not finalized, not built.

## 8. Membership flexibility: modular sizing strategy

I want fixed-size circles for v1 — the collateral formula's "potential group loss" term depends on a knowable, stable member count, and a flexible/mid-cycle-join model breaks that assumption (pot size shifts mid-cycle, the collateral formula's inputs become a moving target, and a late joiner's position in the rotation needs its own design pass). Flexible sizing is a real feature I want eventually, just not one I want to solve at the same time as the core trust model.

**Decision: define circle sizing/membership rules behind a `CircleSizingPolicy` interface (Strategy pattern)**, so the rest of the system — the collateral formula, the default waterfall, scheduling — depends only on the interface, never on which sizing strategy is active.

Interface shape (illustrative, not final):
```
CircleSizingPolicy:
  canMemberJoin(circle, joinRequest) -> boolean
  calculatePotSize(circle) -> amount
  getTotalRounds(circle) -> int
  calculatePotentialGroupLoss(circle, member, payoutPosition) -> amount
```

v1 implements `FixedSizeCircleSizingPolicy` (member count locked before round 1 starts). Each `Circle` references which policy it uses. This same interface is also the natural home for a possible gated-circle variant — hand-picked membership with a relaxed collateral formula (Section 7) — as its own policy implementation, without touching the shared collateral/waterfall/scheduling code. Future work can also add `FlexibleEnrollmentSizingPolicy` (join allowed until round 1 starts) or, further out, a true mid-cycle-join variant.

**Why this matters beyond just "clean code":** it means I can honestly say the fixed-size decision for v1 was a deliberate scope choice, not a limitation baked into the architecture — and I have a concrete plan (a new policy implementation) for extending it, rather than a vague "we'd need to rebuild it" answer if asked about it.
